# User Stories, Use Cases и NFR

## Истории пользователей

US-01. Как студент, я хочу просмотреть аудитории с вместимостью, чтобы подобрать помещение. Приёмка: список доступен после входа, содержит название, вместимость и идентификатор.

US-02. Как преподаватель, я хочу забронировать проектор на выбранное время, чтобы провести занятие. Приёмка: будущий интервал до 8 часов принимается, пересекающийся подтверждённый интервал возвращает 409; соседние интервалы допустимы.

US-03. Как пользователь, я хочу безопасно повторить запрос после обрыва связи. Приёмка: одинаковые пользователь, ключ и нормализованное тело дают тот же ID; другой интервал с прежним ключом отклоняется.

US-04. Как пользователь, я хочу отменить собственную бронь. Приёмка: статус меняется на cancelled, интервал доступен снова, повторная отмена не создаёт новое событие. Чужая бронь недоступна для отмены.

US-05. Как администратор, я хочу добавлять аудитории и оборудование. Приёмка: student получает 403; аудитория без положительной вместимости получает 422; новый ресурс появляется в booking-проекции после события.

US-06. Как пользователь, я хочу видеть подтверждения и отмены в уведомлениях. Приёмка: доступен только собственный inbox; повторная доставка одного event_id не дублирует уведомление.

US-07. Как администратор, я хочу исследовать аудит и архив. Приёмка: student получает 403; событие доступно в горячем аудите, после архивирования — в отдельном хранилище. Архивирование не удаляет горячую запись до успешного upsert в архив.

## UC-01: бронирование

Актор: студент/преподаватель. Предусловия: действующий токен, пользователь и ресурс уже доставлены в проекцию. Триггер: POST /api/bookings/bookings с Idempotency-Key.

Основной поток: пользователь выбирает ресурс; указывает начало и конец с часовым поясом; сервис нормализует время в UTC; проверяет владельца ключа и проекции; транзакция записывает бронь и outbox; PostgreSQL подтверждает отсутствие пересечения; API возвращает 201; outbox-публикатор отправляет событие; уведомления и аудит обновляются независимо.

Альтернативы: невалидный интервал — 422; токен отсутствует/истёк — 401; проекция ещё не готова — 409 с предложением повторить; ресурс занят — 409; повтор с тем же ключом — прежняя бронь; Kafka недоступна — бронь сохраняется, outbox ждёт восстановления; PostgreSQL недоступна — операция не подтверждается. Постусловие: одна подтверждённая бронь, событие сохранено надёжно в том же commit.

## UC-02: отмена

Актор: владелец или администратор. Предусловие: бронь существует. Пользователь отправляет DELETE; сервис блокирует строку; проверяет права; меняет статус и записывает outbox в одной транзакции; возвращает cancelled. Альтернативы: чужая бронь — 403; отсутствующая — 404; повторная отмена — 200 без нового события. Постусловие: интервал освобождён, уведомление доставляется асинхронно.

## UC-03: добавление ресурса

Актор: администратор. POST в rooms либо equipment; проверка полей; ресурс и событие записываются одной транзакцией; кэш инвалидируется. Booking-сервис получает ресурс через Kafka. При временном отставании проекции бронь отклоняется, а не принимается для неизвестного ресурса.

## Нефункциональные требования

Ниже целевые требования промышленного варианта, а не результаты измерений локального стенда.

| ID | Требование | Проверка |
|---|---|---|
| NFR-01 | 0 пересекающихся confirmed-броней для одного ресурса | 100 параллельных запросов на один интервал: 1 успех, остальные 409 |
| NFR-02 | p95 чтения <300 мс, записи <500 мс при 50 RPS и 100k броней | Нагрузочный тест через gateway; лимит тестового IP повысить отдельно |
| NFR-03 | 99.5% доступности API в месяц | Внешняя HTTP-проба, месячный SLI; HA-развёртывание |
| NFR-04 | p95 event-to-inbox <5 с при здоровом Kafka | Разница времени commit и получения уведомления |
| NFR-05 | Не терять committed-брони при остановке приложения | Kill после commit, рестарт, доставка outbox |
| NFR-06 | Повторная доставка не повторяет бизнес-эффект | Replay события, подсчёт inbox/notifications |
| NFR-07 | DB RPO ≤24 ч и RTO ≤2 ч | Суточный backup и квартальная тренировка восстановления |
| NFR-08 | TLS, SSO/OIDC, запрет межсервисного чтения чужой DB | Security review production-конфигурации |
| NFR-09 | 10 RPS/IP, burst 20, превышение 429 | Серия запросов в gateway |
| NFR-10 | Кэш восстанавливаемый, TTL ≤30 с | Остановка Valkey, успешный ответ из PostgreSQL |
| NFR-11 | Горячий аудит 30 дней, архив минимум 1 год | Проверка переноса и backup; автоудаление архива в MVP отсутствует |
| NFR-12 | Масштабирование consumer до 6 реплик на группу | 6 партиций, consumer lag, rebalance |

Часовые пояса передаются явным offset, хранение UTC. Интервалы полуоткрытые [start,end). Максимальная длительность 8 часов. Периодическая очистка sent-outbox/inbox должна учитывать replay retention; в MVP автоматической очистки нет.
